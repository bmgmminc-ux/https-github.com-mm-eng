# 설계 검토 — 직원 공동 입력 + 이윤은 상위 관리자만 열람

작성 2026-09-13 · 대상 시스템 myungmoon.netlify.app (단일 HTML + Supabase) · 상태: **대표 결정 반영(2026-09-13) · 실배포 시점에 착수**

## 1. 요구

- 매입·출역·거래처·일용직 같은 **입력은 직원들과 함께** 한다.
- **이윤·이익률·계약금액 같은 돈의 결론은 상위 관리자(대표·관리자)만** 본다.
- 두 사람 이상이 같은 현장을 동시에 입력해도 서로의 입력을 지우지 않는다(2단계에서 해결됨).

## 2. 지금 구조로는 왜 안 되는가 — 세 가지 사실

1. **역할을 브라우저가 스스로 정한다.** 로그인 직후 `mmRoleFor(이메일)` 로 역할을 고르고 `mm-auth` 에 저장한다(index.html 19607). 서버의 `user_profiles.role` 은 있지만 화면 판정에 쓰이지 않는다. 직원이 개발자 도구에서 역할 값만 바꾸면 관리자 화면이 열린다.
2. **접근 규칙이 '만든 사람' 기준이고, 부모·자식이 어긋난다.** 현장(`projects`)은 `owner_id = 본인` 에 더해 대표·관리자 전체 읽기 정책이 있지만(00001_base_schema.sql 174·242·245), 매입·기성·원가분류(`cost_items`·`billing_items`·`project_costs`)는 여전히 **현장 소유자 본인만** 접근한다(179·181·177). 대표가 직원이 만든 현장은 보이는데 그 매입은 못 보는 구조다. 회사 단위 규칙이 없다.
3. **데이터 전부가 브라우저에 내려온다.** 내려받기는 현장·매입·기성·기타수익을 통째로 localStorage 에 넣는다. 화면에서 이윤을 가리는 것은 '커튼'일 뿐, 직원 브라우저 안에는 계약금액과 이윤 계산 재료가 그대로 있다. **화면 숨김만으로는 요구를 충족할 수 없다.**

## 3. 설계 원칙 하나

**보여주지 않을 것은 서버가 아예 보내지 않는다.** 역할 판정과 데이터 차단을 모두 Supabase(RLS) 쪽에 두고, 앱은 "받은 것만 그린다". 받지 못한 칸은 0 이 아니라 **"관리자 전용"** 으로 표시한다(정직한 빈 상태 원칙과 같다).

## 4. 데이터 분리 — 무엇을 나누는가

돈의 결론은 계약금액에서 나온다(이윤 = 계약 + 기타수익 − 원가). 따라서 **계약금액과 매출 계열을 별도 표로 떼어** 관리자만 읽게 하면, 직원은 매입을 전부 다뤄도 이윤을 알 수 없다.

| 자료 | 어디에 | 직원(staff) | 관리자(manager) | 대표(admin) |
|---|---|---|---|---|
| 현장 이름·발주처·기간·상태·주소 | `projects` (코어) | 읽기·쓰기 | 읽기·쓰기 | 읽기·쓰기 |
| 계약금액·추가계약·예산 항목·목표 이익률 | **`project_finance`(신설)** | **없음** | 읽기·쓰기 | 읽기·쓰기 |
| 기성 청구·수금 | `billing_items` | **없음** (또는 회차·날짜만) | 읽기·쓰기 | 읽기·쓰기 |
| 기타수익 | `other_income_items` | 없음 | 읽기·쓰기 | 읽기·쓰기 |
| 매입(외주·자재·인건·직불…) | `cost_items` | 읽기·쓰기 | 읽기·쓰기 | 읽기·쓰기 |
| 출역·일용직·거래처 | `attendance`·`workers`·`vendors` | 읽기·쓰기 | 읽기·쓰기 | 읽기·쓰기 |
| 임계값(원가 한계·이익 목표) | `thresholds` | 없음 | 읽기 | 읽기·쓰기 |
| 첨부 증빙 | storage `mm-attachments` | 자기 회사 현장 것 | 전체 | 전체 |
| 사용자·역할 관리 | `user_profiles` | 자기 것 | 읽기 | 읽기·쓰기 |

`project_finance` 는 `project_id` 를 기본키로 두고 `contract_orig`·`contract_add`·`budget_items`·`profit_target` 을 `projects` 에서 옮긴다. 옮긴 뒤 `projects` 의 해당 컬럼은 비운다(과도기에는 뷰로 합쳐 옛 화면을 유지할 수 있다).

**원가율에 대한 결정이 필요하다.** 원가율 = 원가 ÷ 매출이라 계약을 모르면 직원 화면에서 원가율·신청률 게이지도 사라진다. 두 갈래다.
- (가) 직원은 진행률·매입 합계·출역만 본다. 원가율 없음. — 가장 단순하고 새는 곳이 없다.
- (나) 직원에게 원가율 **구간만**(양호/주의/초과) 보여준다. 서버가 구간 값만 계산해 내려준다(정확한 계약금액은 안 나감). — 함수 하나 추가로 가능.
**결정: (나) 구간만.** 구현은 8-1 참조.

## 5. 접근 규칙(RLS) — 회사 기준 + 역할

- `user_profiles.company_id` 를 필수로 하고, `projects` 에 `company_id` 를 추가한다(신규 현장은 만든 사람의 회사로 자동 채움).
- 모든 정책을 **"같은 회사"** 기준으로 통일한다. 자식 표(`cost_items` 등)는 `project_id → projects.company_id` 로 판정한다. 지금의 owner 기준 정책은 제거한다.
- 역할은 서버 함수 `my_role()`(이미 있음, 00001 238행)로 판정한다. 값은 `staff` / `manager` / `admin` 세 가지로 정리한다(지금의 `user`→`staff`, `ceo`→`admin`).
- `project_finance`·`billing_items`·`other_income_items`·`thresholds` 는 `my_role() in ('manager','admin')` 일 때만 select/write.
- 삭제(현장 영구 삭제)는 `admin` 만.
- 첨부 저장소 정책은 폴더 첫 칸이 현장 id 인 현재 경로를 그대로 두고, 그 현장이 같은 회사인지로 판정한다(20260826_triage.sql 의 uid 폴더 정책은 폐기).
- 실시간 구독은 RLS 를 자동으로 따르므로 직원 브라우저에는 재무 행 이벤트가 오지 않는다.

## 6. 앱 변경

1. **역할 출처 교체**: 로그인 후 `user_profiles.role` 을 읽어 `mm-auth.role` 을 채운다. `mmRoleFor(이메일)` 은 최초 관리자 지정용 폴백으로만 남긴다. 화면 게이팅(`mmPerm.canManage` 등)은 그대로 쓰되 값의 출처만 서버가 된다.
2. **내려받기 분기**: 직원은 `project_finance`·`billing_items`·`other_income_items` 를 요청하지 않는다(요청해도 RLS 가 빈 배열을 준다). 로컬 현장 객체에서 그 필드는 `undefined` 로 둔다.
3. **표시 슬롯 처리**: 이윤·이익률·계약금액을 그리는 자리(id 목록: `ov-hero-profit`·`ov-hero-contract`·`pjd-hero-profit`·`pjd-profit-rate-mega`·`pjd-rev-contract`·`pjbx-h-profit`·`pjd-hero-cost-rate` 등 30여 곳)에서 값이 `undefined` 면 **"관리자 전용"** 을 찍고 게이지는 비운다. 라이브 존·선택 기간 존은 이미 어댑터(`rnLive.api`) 한 곳을 거치므로 거기서 한 번에 처리한다.
4. **올리기 분기**: 직원 push 는 매입·출역·마스터 함수만 부른다(`mm_upsert_cost_items` 등 이미 있음). 현장 코어는 `projects` upsert 로, 재무는 새 함수 `mm_upsert_project_finance` 로 나눈다. 직원 기기에는 재무 필드가 없으므로 실수로라도 덮어쓸 수 없고, 서버도 거부한다.
5. **직원용 화면 집합**: 전체 현황(직원판) — 진행 현장·오늘 출역·이번 달 매입 합계·미등록 거래처 경고. 현장 상세(직원판) — 매입 입력·첨부·출역. 기성·보고서·원가 분산·임계값·사용자 관리는 메뉴에서 빠진다. 같은 코드에 `data-role` 속성으로 분기하므로 파일은 하나다.
6. **동시 입력**: 2단계에서 매입은 행 단위 병합이므로 직원 여럿이 같은 현장을 동시에 입력해도 서로 지우지 않는다. 관리자가 계약금액을 고치는 것과 직원이 매입을 넣는 것은 표가 달라 충돌하지 않는다.

## 7. 이행 순서

| 단계 | 내용 | 대표 SQL 실행 | 앱 배포 | 규모 |
|---|---|---|---|---|
| R1 | `company_id` 도입 + 회사 기준 RLS 로 전면 교체 + `my_role()` 값 정리 | 1회 | 소(역할 출처 교체) | 중 |
| R2 | `project_finance` 신설·이관 + 재무 표 정책 + `mm_upsert_project_finance` | 1회 | 중(내려받기·올리기 분기, 표시 슬롯 30여 곳) | 대 |
| R3 | 직원용 화면 집합·메뉴 게이팅·"관리자 전용" 표시 · **다운로드 계열 제거 + PDF 보고서 직원판** · `mm_cost_band` 구간 표시 | 1회(`mm_cost_band`) | 중 | 중 |
| R4 | 첨부 저장소 회사 기준 정책 + 사용자 초대·역할 관리 화면 정리 | 1회 | 소 | 소 |

R1 과 R2 는 순서를 지켜야 한다(회사 기준이 먼저). 각 단계는 1단계·2단계와 같은 방식으로 검증한다: 가짜 클라이언트 실증 → 픽스처 스모크 → 실환경(직원 계정 하나를 만들어 재무 행이 실제로 안 내려오는지 REST 로 확인).

## 8. 대표 결정(2026-09-13)

1. **직원에게 원가율은 구간만 보인다** — 양호 · 주의 · 초과. 정확한 비율·계약금액은 내려가지 않는다.
2. **직원은 데이터를 내려받을 수 없다. PDF 보고서 작성만 가능하다.**
3. 기성 청구는 직원에게 보이지 않아도 된다 → 가장 단순한 쪽(완전 숨김)으로 간다.
4. 역할은 직원 · 관리자 · 대표 세 단계로 충분하다.

### 8-1. 원가율 구간 — 서버가 구간만 계산해서 준다
- SQL 함수 `mm_cost_band(project_id)` 를 두고 **security definer** 로 만든다. 함수 안에서만 `project_finance`(계약)·`cost_items`(원가)·`thresholds`(한계)를 읽어 `'good' | 'warn' | 'crit'` 한 단어만 돌려준다. 호출자가 직원이어도 계약금액은 함수 밖으로 나오지 않는다.
- 직원 화면의 원가율 게이지 자리는 숫자 대신 색 띠(양호 초록 · 주의 노랑 · 초과 빨강)와 글자만 그린다. 관리자 화면은 지금처럼 비율과 금액을 그린다.
- 경보(원가 초과 임박 등)도 직원에게는 구간 이름으로만 나간다.

### 8-2. 다운로드 금지 — 무엇을 막고, 무엇은 막을 수 없는가
막는 것(직원 역할일 때 버튼·기능 자체를 없앤다):
- 견적 Excel · CSV 내보내기(매입·기타수익·거래처·일용직) · 백업 내보내기(JSON 번들 `v3-139`) · 현장 복사 · 붙여넣기용 표 복사 버튼.
- 화면의 "다운로드" 계열 액션 전부 — `data-role="staff"` 에서 CSS 로 감추는 것에 그치지 않고, 실행 함수 입구에서 `mmPerm.canManage()` 를 확인해 거부한다(버튼을 개발자 도구로 되살려도 동작하지 않게).
- PDF 보고서만 남긴다. 보고서 생성기는 역할을 보고 **직원용 보고서에는 재무 항목을 넣지 않는다**(계약·이윤·기성 없음, 원가율은 구간만).

막을 수 없는 것(정직하게 적어 둔다):
- 직원이 화면에서 **볼 수 있는** 자료(자기 회사 현장의 매입 목록·출역·거래처)는 브라우저 안에 있으므로, 화면 캡처나 개발자 도구로 읽어 가는 것까지 코드로 막을 수는 없다. 이 부분은 취업규칙·비밀유지 서약 같은 운영 규칙의 영역이다.
- 반면 **서버가 보내지 않는 자료(계약·이윤·기성·기타수익·임계값)는 어떤 방법으로도 직원 브라우저에 존재하지 않는다.** 다운로드 금지의 실질적 보증은 여기에 있다.

### 8-3. 기성 청구
- 직원 역할은 `billing_items` 를 요청하지 않고 서버도 주지 않는다. 현장 상세의 기성 탭·수금률 게이지는 직원 화면에서 빠진다.

## 9. 하지 않을 것

- 화면만 가리고 데이터는 그대로 내려보내는 방식. 요구를 충족하지 못한다.
- 직원용 별도 앱을 새로 만드는 것. 같은 파일에서 역할로 분기하는 편이 유지가 쉽다.
